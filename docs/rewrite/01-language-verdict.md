# Language verdict: Go, with Rust kept on the bench

## Decision

The rewrite proceeds in **Go**. The hot-path core already exists in
`gocore/` and is proven against golden data generated by the Python
reference. Rust remains the right answer for a different deployment shape,
not for this one; the reasoning and the measurements behind that call are
below.

## What was actually measured

Both implementations run the identical pipeline on the identical fixture:
`gocore/testdata/stream.txt`, a 2,005-frame Anthropic SSE response with
text, thinking, tool-call deltas, and multi-byte content. Per frame each
implementation performs incremental frame splitting, event-name extraction,
a cached payload parse, failure scanning, and retention byte accounting.
100 iterations per process, warm-up discarded, same two-core machine.

| Metric | Python 3.14.10 (optimized) | Go 1.22.12 |
| --- | --- | --- |
| Latency per request | 83.1 ms | 5.4 ms |
| Throughput | 12.0 req/s | 186 req/s |
| Relative speed | 1.0x | **15.4x** |
| Live memory footprint | 1,743 KiB peak (tracemalloc) | 348 KiB live heap after GC |
| Allocation churn | reference | 3.0 MiB/request, 40,135 allocs |

Reproduce with `.venv/bin/python bench_local/bench_golden.py` and
`go run ./cmd/bench` from `gocore/`. The Python side already includes the
full optimization pass described below; Go is measured against the fastest
Python, not the original one.

For scale, the end-to-end TestClient benchmark for the whole HTTP stack
moved from 272.20 ms to 118.94 ms per request (3.7 to 8.4 req/s) through
pure-Python work before any Go was written. Go takes the component hot path
another order of magnitude beyond that.

## Why not Rust, the theoretically faster option

Rust would likely beat the Go number by another 1.5-2.5x on this
microbenchmark: serde_json or simd-json, zero-copy tokenization, and no GC
whatsoever. That ceiling is real, but four facts make Go the correct system
decision here.

1. **The measured 15x already exceeds the requirement.** A local proxy
   spends its wall clock waiting on upstream model streams that emit tens of
   tokens per second. The per-frame budget is now microseconds in Go; the
   remaining latency is network and model time no language can reclaim.
2. **The workload is concurrent I/O, not number crunching.** Every upstream
   connection is a long-lived SSE pump with cancellation, timeouts, and
   fan-out. Goroutines and `context` express this directly; tokio tasks and
   `Arc<Mutex<..>>` state machines express it at a much higher cognitive
   cost, most visibly in the stream recovery and tool-buffer state machines.
3. **The surface area is 75,000 lines across 423 modules.** Sixty-one
   providers, twelve launchers, SQLite stores, Telegram and Discord
   bridges, desktop integration, and an admin UI all need to move. Go's
   uniform standard library, fast compile cycle, and low conceptual surface
   keep that port reviewable and shippable. Rust's type system pays off on
   core engines; it taxes a broad, mostly glue-shaped codebase.
4. **Distribution favors one static binary.** Users today install a Python
   runtime through uv and pin exactly 3.14.10. A Go build produces one
   static binary per OS/architecture with no runtime dependency and trivial
   cross-compilation, including a pure-Go SQLite driver, so the install
   story collapses into a single download.

The honest Rust case is a different product: a high-density edge gateway
holding tens of thousands of concurrent streams per node under a hard memory
envelope. FCC runs on developer laptops and small self-hosted instances.
The Go core is deliberately stdlib-only with golden, language-agnostic
parity fixtures, so a future Rust port of individual packages remains a
mechanical option if the deployment shape ever changes.

## Go risks and how they are contained

- **No sum types.** The event state machines in `delivered_response.py`
  rely on exhaustive kind matching. Go gets explicit event kinds plus
  default-to-unsafe handling, mirroring the Python code's habit of setting
  an unsafe reason on anything unrecognized rather than silently accepting
  it.
- **Decimal precision.** Go decodes with `json.Number` everywhere; the
  parity fixture includes a fractional payload that fails the test if the
  wire form is ever float-rounded. Ledger and hashing paths stay stringly
  typed end to end.
- **GC tail latency.** Go pause times are sub-millisecond and irrelevant
  against multi-second model responses. The benchmark reports both churn
  and live heap so regressions stay visible.
- **Unicode line separators.** Only CR, LF, and CRLF delimit SSE frames.
  U+2028 and U+2029 inside JSON must never split a frame; the randomized
  golden streams pin this, and a fixture-generator bug that violated it was
  caught by the Go tests during development.

## Sandbox note

The Rust toolchain could not be installed in the build environment:
`static.rust-lang.org` and GitHub release-asset redirects are outside the
network allowlist. The Rust figures above are therefore engineering
estimates, clearly labeled. Every Go number in this document is measured
from code in this repository; the Go toolchain itself was bootstrapped from
source through the 1.4 to 1.22 chain because no prebuilt binary host was
reachable.

## State of the Python implementation

The rewrite does not start from a slow Python baseline. The profiling-led
pass on the current tree, all covered by the existing 9,794-test suite
(9,794 passed, 10 skipped after the changes), landed:

- module-level compiled SSE regexes instead of per-call pattern strings;
- a bounded FIFO payload cache cutting per-frame JSON parses from three to
  one, with deep-copy-before-mutation preserved at every call site;
- framing-only outcome middleware that performs zero JSON decoding on
  healthy streams, with a C-level substring rejection before any splitting;
- an LF-only split fast path in the SSE decoder, checked byte for byte
  against the general scanner by randomized property tests;
- a monotonic byte-size estimator replacing per-frame `simplejson`
  serialization in retention accounting;
- hoisted frozenset constants replacing per-frame literal allocation in the
  delivery state machine.

These changes keep the Python product correct and fast while the Go core
matures, and they define the exact semantics the Go port must reproduce.
